## 1. System Classification

**System Type:** Conversational Agent (stateful, multi-stage)

**Description:**
OttoBot Phase 1 is a stateful Tagalog/Taglish AI sales agent that carries full appointment-booking conversations on behalf of Filipino SMB owners (dental clinics, aesthetics studios, real estate brokers). The system runs as a LangGraph state machine with 7 explicit conversation stages — intro, qualify, pitch, objection_handling, propose_appointment, confirm, escalate — persisted to Supabase Postgres via PostgresSaver. A LiteLLM Router provides model fallbacks (Groq/Llama 4 Maverick primary, Gemini Flash, Mistral) so the agent remains available under free-tier rate limits. A FastAPI WebSocket server streams each LLM token to a Vite+React split-screen demo UI showing both the lead's chat and the business owner's monitoring panel in real time. "Good" means: the agent never breaks character, always responds in the lead's language register (Tagalog/Taglish/English), escalates to the human owner within 1 turn of a 2-of-3 composite signal firing, and books appointments with zero hallucinated details.

**Critical Failure Modes:**
1. **Cascading 429s under concurrent load** — Groq free tier enforces per-minute RPM limits. If multiple WebSocket sessions fire LLM calls simultaneously, all requests to the primary model fail and the fallback chain also saturates (Gemini Flash has its own free-tier limits). The agent silently returns empty responses or throws uncaught exceptions, breaking all active conversations simultaneously rather than degrading gracefully.
2. **PostgresSaver schema migration breaks state replay** — On `langgraph-checkpoint-postgres` version upgrades, the `checkpoint_migrations` table versioning increments. If `.setup()` is not re-run after upgrading, or if the migration runs partially due to a network failure, existing thread checkpoints become unreadable. The agent loses conversation history silently: `graph.get_state()` returns `None` instead of raising, and the agent restarts every thread from stage 0 as if the lead is new.
3. **SalesGPT fork coupling: Jinja2 template renders at conversation start with stale or missing BusinessProfile fields** — The BusinessProfile Pydantic model validates at instantiation time, but the Jinja2 template rendering (`template.render(**profile.dict())`) happens inside the node function at runtime. A missing optional field (e.g., `pricing` left as `None`) causes a `jinja2.exceptions.UndefinedError` that surfaces mid-conversation, not at startup. Because the error is thrown inside a LangGraph node, the graph catches it as a node failure and the WebSocket connection drops without a user-visible error message.

## 1b. Domain Context

> Researched by `gsd-domain-researcher`. Grounds the evaluation strategy in domain expert knowledge.

**Industry Vertical:** Filipino SMB sales — dental clinics, aesthetics studios, real estate brokers

**User Population:** Two distinct populations. (1) Leads: Filipino consumers (ages 20-45) who received a cold or warm outreach message via Facebook Messenger or SMS, communicating in Tagalog, Taglish, or English. (2) Business owners: Filipino SMB owners (dental clinic managers, aesthetics studio operators, real estate brokers) who review lead status and receive escalation alerts via a monitoring panel.

**Stakes Level:** High

**Output Consequence:** A lead who receives a well-timed, appropriately-toned agent message books an appointment that converts to revenue. A lead who receives a tone-deaf, culturally off, or inaccurate message (wrong pricing, wrong service, bot-like phrasing) disengages permanently — in the Filipino context, public complaints on Facebook are common. A missed escalation signal means the business owner does not call back a hot lead, and the booking window closes.

### What Domain Experts Evaluate Against

---

**Dimension:** Register matching (pakikisama sa wika ng kausap)

Good (Filipino sales manager would accept): Agent mirrors the lead's exact code-switch ratio. If the lead writes "Hi! Interested po ako sa whitening, magkano?" the agent responds in Taglish at the same formality level — not full Tagalog, not full English, and not more formal than the lead.

Bad (Filipino sales manager would flag): Agent responds in full English to a Taglish lead ("Hello! Our whitening package starts at P1,500."), or uses overly formal Tagalog ("Magandang araw po. Ang aming serbisyo ay...") when the lead is casual. Either registers as corporate and impersonal — the lead loses trust immediately.

Stakes: Critical

Source: Philippine AI chatbot practitioners (botsatwork.ph, nextgenai.ph) — "80% of Filipinos type in Taglish; any bot that can't handle it out of the box is disqualifying." Filipino consumer behavior: casual Taglish is the register of trust in peer-to-peer commerce.

---

**Dimension:** Honorific use and persona warmth

Good: Agent uses its designated persona name consistently (Ate Ana for dental, Ate Bea for aesthetics, Kuya Marco for real estate) in every greeting and closing. Uses "po" and "opo" with leads who use them. Does not use the lead's first name without being given it.

Bad: Agent drops the persona name mid-conversation, switches honorific level inconsistently (uses "po" in one message, drops it the next), or addresses the lead by a first name it was never given. Filipino leads read this as the "person" they were talking to has been replaced — breaks rapport.

Stakes: High

Source: Filipino sales manager practitioner knowledge; honorific use is a well-established social norm in Philippine service commerce. Persona consistency is a baseline expectation in Messenger-based SMB sales.

---

**Dimension:** Appointment detail accuracy (no hallucinated slots or prices)

Good: Agent proposes only time windows the business owner has set as available. States pricing in Philippine Peso with the correct range from the BusinessProfile. Never invents a service, slot, or price not present in the business profile.

Bad: Agent offers "Tuesday 3pm" when the clinic's availability is weekdays 9am-12pm only. States "P800 for whitening" when the BusinessProfile says "P1,500-P2,500." Any hallucinated detail — even one — breaks the booking and destroys the business owner's trust in the system.

Stakes: Critical

Source: Core product requirement (AGENT-04, APPT-02); standard for appointment-booking conversational agents in healthcare and aesthetics contexts. A single incorrect price or time slot communicated to a lead creates a real customer service incident.

---

**Dimension:** Escalation timing (hot lead handoff)

Good: Agent escalates to the human business owner within 1 conversation turn of a 2-of-3 signal firing. The escalation message to the lead includes the business phone number and a natural bridge phrase ("Para mas mabilis po, pwede na kayong i-contact si [name] directly..."). The owner panel shows an alert within 5 seconds.

Bad: Agent continues pitching after a lead says "gusto ko na mag-book bukas" — failure to escalate a clear booking intent. Or agent escalates too early (after the first "magkano?" inquiry) before the lead has shown genuine intent — wastes the owner's time and conditions them to ignore alerts.

Stakes: Critical

Source: Decision D-09 (2-of-3 composite signal logic); core business value proposition of OttoBot. In Filipino sales, the booking window is brief — leads move fast once interest peaks. Late escalation = lost booking.

---

**Dimension:** Objection handling without pressure tactics

Good: When a lead says "mahal naman," the agent acknowledges the concern, re-frames value ("naka-include na po ang consultation at whitening kit"), and offers a softer next step ("pwede po kayong mag-schedule ng libreng consultation para makita ang full package"). Does not repeat the same pitch twice in a row.

Bad: Agent repeats the same price or service description verbatim after an objection. Applies overt pressure ("limited slots only po!") without the business owner having authorized urgency messaging. Uses English-only objection responses when the lead is Taglish. Filipino leads interpret repeated pitching as pushy and will ghost the conversation.

Stakes: High

Source: Filipino consumer sales norms — high-pressure tactics are culturally associated with scams in online commerce. SalesGPT stage definitions (objection_handling stage); Filipino sales practitioner knowledge.

---

### Known Failure Modes in This Domain

1. **Ghost trigger: lead uses Filipino politeness phrases that mimic disengagement but signal interest.** "Sige po, i-iisip ko muna" ("I'll think about it") is often the lead's way of asking for a softer close or more information — not a rejection. An agent that routes this to a closed/lost state misses a recoverable lead. Filipino politeness norms make direct rejection rare; the agent must distinguish polite deflection from genuine disinterest using conversation context, not surface phrase matching.

2. **Persona collapse mid-conversation.** If the Jinja2 template renders correctly on turn 1 but the stage instruction injected on later turns contradicts the persona (e.g., stage prompt says "you are an assistant" without restoring persona name and industry context), the LLM gradually drops the Ate Ana / Kuya Marco voice and reverts to a generic assistant tone. Business owners notice this as "the agent stopped sounding like us."

3. **Price anchoring error in multi-service conversations.** When a lead asks about multiple services in one message ("magkano ang whitening at braces?"), the agent may transpose prices between services or blend them into a fabricated combined rate. Filipino consumers in aesthetics and dental are price-sensitive and will screenshot incorrect quotes and share them — a business liability, not just a UX issue.

4. **Escalation alert fatigue: false positives condition the owner to stop responding.** If the 2-of-3 escalation logic fires on low-intent interactions (e.g., lead asks "may parking ba kayo?" triggering fast-response-cadence signal), the business owner receives too many alerts and starts ignoring them. When a genuine hot lead escalates, the owner misses it. The escalation precision rate matters more than recall in this domain.

### Regulatory / Compliance Context

**Republic Act 10173 — Data Privacy Act of 2012 (DPA), Philippines:**
The agent collects lead names, contact numbers, and conversation content (personal data under DPA). As a Personal Information Controller (PIC), the business owner operating OttoBot must: (1) obtain consent before collecting data, disclosed in the initial message; (2) state the purpose of data collection (appointment booking, sales follow-up); (3) appoint a Data Protection Officer (DPO) if operating at scale; (4) register with the National Privacy Commission (NPC) if handling sensitive or large-scale personal data. Violations carry penalties up to ₱5 million. Advisory No. 2024-04 (NPC, December 2024) explicitly requires that AI systems performing automated decisions that affect data subjects must provide mechanisms for human intervention — this is satisfied by OttoBot's escalation-to-human architecture.

**NPC Advisory No. 2024-04 — Guidelines on Artificial Intelligence:**
Requires transparency (the lead must know they are interacting with an AI agent, not a human), legitimate purpose, and proportionality in data processing. The agent persona (Ate Ana, Ate Bea, Kuya Marco) may create ambiguity about AI vs. human identity — the intro message must disclose the AI nature of the interaction clearly.

**No additional regulations identified:** HIPAA does not apply (Philippines jurisdiction). There is no specific Philippine telemarketing law equivalent to TCPA, but the Cybercrime Prevention Act (RA 10175) applies to unsolicited bulk messaging — relevant when OttoBot moves to SMS broadcast in Phase 4.

## 2. Framework Decision

**Selected Framework:** LangGraph 0.2.x + LiteLLM 1.x

**Version:** LangGraph 0.2.x, LiteLLM 1.x (pin exact versions in pyproject.toml)

**Rationale:**
The 7-stage bidirectional conversation graph (D-08) and PostgresSaver persistence (DEMO-03) are native LangGraph features with zero impedance mismatch. LiteLLM handles the Groq/Gemini/Mistral fallback router natively via YAML config without custom routing code. PostgresSaver into Supabase provides a single persistence layer for both agent state and conversation history, eliminating the need for a second datastore.

**Alternatives Considered:**

| Framework | Ruled Out Because |
|-----------|------------------|
| CrewAI + LiteLLM | Coarse checkpointing and no native bidirectional graph edges make D-08 (backward routing) and D-09 (2-of-3 composite escalation scoring) painful to implement correctly |
| LangChain Agents (non-graph) | No first-class state graph — would require manual stage tracking outside the framework, losing LangGraph's time-travel debugging and PostgresSaver |

**Vendor Lock-In Accepted:** No — LiteLLM provides model-agnostic routing; no OpenAI/Anthropic vendor lock-in.

### Entry Point Pattern
```python
"""
Minimal stateful conversational agent: LangGraph + AsyncPostgresSaver + LiteLLM Router.
Copy-paste runnable — fill in DB_URI and API keys from env.
"""
import asyncio, os
from typing import Annotated, Literal
from langgraph.graph import StateGraph, END
from langgraph.graph.message import add_messages
from langgraph.checkpoint.postgres.aio import AsyncPostgresSaver
from litellm import Router
from typing import TypedDict

# --- LiteLLM Router (mirrors CONTEXT.md D-07 provider stack) ---
router = Router(
    model_list=[
        {
            "model_name": "chat",
            "litellm_params": {
                "model": "groq/meta-llama/llama-4-maverick-17b-128e-instruct",
                "api_key": os.environ["GROQ_API_KEY"],
                "rpm": 30,          # Groq free-tier hard limit; prevents silent 429 cascade
                "tpm": 6000,
            },
        },
        {
            "model_name": "chat",
            "litellm_params": {
                "model": "gemini/gemini-1.5-flash",
                "api_key": os.environ["GEMINI_API_KEY"],
                "rpm": 15,
            },
        },
        {
            "model_name": "chat",
            "litellm_params": {
                "model": "mistral/mistral-small-latest",
                "api_key": os.environ["MISTRAL_API_KEY"],
            },
        },
    ],
    fallbacks=[{"chat": ["chat", "chat"]}],   # tries each deployment in order
    num_retries=2,
    retry_after=1,
    routing_strategy="usage-based-routing-v2",
)

# --- LangGraph State ---
STAGES = Literal["intro", "qualify", "pitch", "objection_handling",
                 "propose_appointment", "confirm", "escalate"]

class ConversationState(TypedDict):
    messages: Annotated[list, add_messages]
    stage: STAGES
    thread_id: str
    escalated: bool

# --- Node: call LLM via LiteLLM router ---
async def agent_node(state: ConversationState) -> ConversationState:
    response = await router.acompletion(
        model="chat",
        messages=state["messages"],
        max_tokens=512,
        temperature=0.7,
    )
    reply = response.choices[0].message.content
    return {"messages": [{"role": "assistant", "content": reply}]}

# --- Edge: hybrid stage transition (D-07) ---
def route_next_stage(state: ConversationState) -> STAGES:
    # Fast rule: explicit escalation signals checked first
    last_msg = state["messages"][-1]["content"] if state["messages"] else ""
    booking_phrases = ["gusto ko mag-book", "magkano", "puwede ba bukas", "schedule"]
    if any(p in last_msg.lower() for p in booking_phrases):
        return "escalate"
    # Default linear progression — LLM stage detection handles ambiguous transitions
    progression = {
        "intro": "qualify", "qualify": "pitch", "pitch": "objection_handling",
        "objection_handling": "propose_appointment", "propose_appointment": "confirm",
        "confirm": "escalate", "escalate": END,
    }
    return progression.get(state["stage"], END)

# --- Build graph ---
builder = StateGraph(ConversationState)
builder.add_node("agent", agent_node)
builder.add_conditional_edges("agent", route_next_stage)
builder.set_entry_point("agent")

# --- Run with AsyncPostgresSaver ---
DB_URI = os.environ["SUPABASE_DB_URI"]  # e.g. postgresql+asyncpg://user:pass@host/db

async def main():
    async with AsyncPostgresSaver.from_conn_string(DB_URI) as checkpointer:
        await checkpointer.setup()   # idempotent — safe to call every startup
        graph = builder.compile(checkpointer=checkpointer)
        config = {"configurable": {"thread_id": "demo-lead-001"}}
        async for event in graph.astream(
            {"messages": [{"role": "user", "content": "Hi, interested sa dental cleaning"}],
             "stage": "intro", "thread_id": "demo-lead-001", "escalated": False},
            config=config,
            stream_mode="values",
        ):
            print(event)

if __name__ == "__main__":
    asyncio.run(main())
```

### Key Abstractions
| Concept | What It Is | When You Use It |
|---------|-----------|-----------------|
| `StateGraph` | The graph builder — nodes are Python functions, edges are routing logic | Define the 7-stage conversation topology; compile with checkpointer to get a runnable graph |
| `AsyncPostgresSaver` | Async Postgres checkpointer from `langgraph.checkpoint.postgres.aio` | Attach via `builder.compile(checkpointer=...)` to persist every state transition to Supabase |
| `add_messages` reducer | Annotated type that appends new messages to the list rather than replacing it | Apply to the `messages` field in `ConversationState` — without it, each node replaces the full message list |
| `astream` / `stream_mode` | Async generator that yields state snapshots or token chunks as the graph runs | Use `stream_mode="values"` for full state per node, `stream_mode="messages"` for token-level streaming to the WebSocket |
| `Router` (LiteLLM) | Load-balancer with fallback chains, per-model RPM/TPM caps, and `usage-based-routing-v2` | Wrap all LLM calls — never call `litellm.acompletion()` directly; always go through the Router instance |

### Common Pitfalls
1. **Calling `.setup()` only once and forgetting it after `langgraph-checkpoint-postgres` upgrades.** The `checkpoint_migrations` table tracks schema version. After a package upgrade, new migrations exist but the table hasn't run them. Symptom: `KeyError` or silent state loss. Fix: always call `await checkpointer.setup()` at application startup — it is idempotent and skips already-applied migrations.
2. **Using the sync `PostgresSaver` inside an async FastAPI app.** `from langgraph.checkpoint.postgres import PostgresSaver` runs blocking psycopg calls on the event loop, causing request timeouts and intermittent deadlocks. Always import from `langgraph.checkpoint.postgres.aio import AsyncPostgresSaver` in an async context.
3. **Creating the `AsyncPostgresSaver` connection outside the async context manager.** `AsyncPostgresSaver.from_conn_string()` is an async context manager (`async with`). Instantiating it as a plain constructor without `await` gives a coroutine object, not a live checkpointer. The compile step succeeds but every `graph.ainvoke()` call raises `AttributeError: 'coroutine' object has no attribute 'aget'`.
4. **Setting `rpm` limits on the Router but forgetting `tpm` limits on Groq free tier.** Groq free tier enforces both RPM (30) and TPM (6,000) limits. A single long conversation can exhaust the TPM cap before hitting the RPM cap. Without `"tpm": 6000` in `litellm_params`, the Router does not track token usage and cannot trigger the fallback before the 429 arrives from Groq.
5. **Bidirectional edges with `add_conditional_edges` pointing to already-visited nodes create infinite loops when the LLM stage detector keeps returning the same stage.** Guard every backward edge with a `visit_count` field in `ConversationState` and add a max-visits check in the routing function (e.g., `if state["visit_count"].get("pitch", 0) >= 3: return "propose_appointment"`).

## 4. Implementation Guidance

**Model Configuration:**

Primary: `groq/meta-llama/llama-4-maverick-17b-128e-instruct` via Groq API.
Fallback 1: `gemini/gemini-1.5-flash` via Google Generative AI API.
Fallback 2: `mistral/mistral-small-latest` via Mistral API.

All calls go through the LiteLLM `Router` singleton with `routing_strategy="usage-based-routing-v2"`.

Per-call parameters:
- `temperature=0.7` — keeps Taglish responses natural; 0.0 makes the agent robotic
- `max_tokens=512` — hard cap; prevents runaway responses and limits per-call cost. Increase to 768 for objection_handling stage only if testing shows truncation
- `rpm=30, tpm=6000` in `litellm_params` for Groq — must be set at Router init, not at call time, or the Router cannot pre-empt the 429

Stage-detection LLM call (D-07, ambiguous transitions): use a separate cheaper model call if cost becomes a concern. Initially use the same Router with a tighter `max_tokens=50` and a classification prompt.

**Core Pattern:**

The 7-stage graph is compiled once at FastAPI startup. Each WebSocket connection maps to a `thread_id`. The graph resumes from the last checkpoint on every incoming message — no session state lives in FastAPI memory.

```python
# api/ws_handler.py — FastAPI WebSocket + LangGraph streaming

from fastapi import WebSocket
from agent.graph import compiled_graph   # graph compiled with AsyncPostgresSaver at startup

async def handle_ws(websocket: WebSocket, thread_id: str):
    await websocket.accept()
    config = {"configurable": {"thread_id": thread_id}}

    async for ws_message in websocket.iter_json():
        user_text = ws_message["text"]
        industry = ws_message.get("industry", "dental")

        # stream_mode="messages" yields (message_chunk, metadata) tuples
        # This gives token-level streaming to the demo UI
        async for chunk, metadata in compiled_graph.astream(
            {"messages": [{"role": "user", "content": user_text}]},
            config=config,
            stream_mode="messages",
        ):
            if hasattr(chunk, "content") and chunk.content:
                await websocket.send_json({
                    "type": "token",
                    "content": chunk.content,
                    "node": metadata.get("langgraph_node"),
                })

        # After stream completes, send the full updated state for the owner panel
        final_state = await compiled_graph.aget_state(config)
        await websocket.send_json({
            "type": "state",
            "stage": final_state.values.get("stage"),
            "escalated": final_state.values.get("escalated", False),
        })
```

**Tool Use:**

- **Jinja2 + BusinessProfile**: The `intro` node renders the system prompt. Load templates with `StrictUndefined` so missing fields raise at the template render call (inside the node), not silently produce empty strings. Validate `BusinessProfile` with Pydantic before passing to Jinja2 — see Section 4b for the retry pattern.
- **Escalation scorer (D-09)**: Lives in `agent/escalation.py`. Called inside `route_next_stage` before any LLM stage-detection call. Returns `True` if 2-of-3 signals fire. Not a LangGraph tool — a plain Python function evaluated in the edge routing function.
- **LiteLLM Router**: Instantiated once in `agent/llm.py` as a module-level singleton. All nodes import and call `router.acompletion(model="chat", ...)`. Never instantiate the Router per-request — it holds connection pools and usage counters that must persist across calls.

**State Management:**

Every state transition is written to Supabase Postgres via `AsyncPostgresSaver` before the next node runs. LangGraph writes the full `ConversationState` snapshot (messages list + stage + escalated flag) as a checkpoint keyed by `thread_id`.

Key operational rules:
- Call `await checkpointer.setup()` at FastAPI startup, inside the lifespan context manager, after the async connection pool is created. The `setup()` method runs all pending migrations idempotently.
- Use `"configurable": {"thread_id": "<lead_uuid>"}` as the graph config. The thread_id should be the lead's unique identifier (not the WebSocket connection ID, which changes on reconnect).
- To resume a conversation: call `graph.astream(None, config=config)` with `None` as input — LangGraph reloads from the last checkpoint automatically.
- To inspect current stage without running the graph: `state = await graph.aget_state(config)`.

**Context Window Strategy:**

Llama 4 Maverick has a 128K context window; Gemini Flash 1.5 has 1M. In practice, constrain the messages passed to the LLM to the last N turns to control cost and latency:

```python
# In agent_node: truncate to last 20 messages + system prompt
MAX_HISTORY = 20
messages_to_send = [system_msg] + state["messages"][-MAX_HISTORY:]
```

For conversations that exceed 20 turns (rare in Phase 1 demo context), summarise the earliest turns with a cheap `mistral/mistral-small-latest` call and replace them with a single `{"role": "system", "content": "Conversation summary: ..."}` message. Implement this summarisation trigger in the `agent_node` function when `len(state["messages"]) > MAX_HISTORY`.

### 4b.1 Structured Outputs with Pydantic

Two Pydantic models are required in Phase 1:

**BusinessProfile** — validated at demo UI industry selection, then passed to Jinja2 template render:

```python
# agent/models.py
from pydantic import BaseModel, Field
from typing import Optional, List
from enum import Enum

class Industry(str, Enum):
    dental = "dental"
    aesthetics = "aesthetics"
    real_estate = "real_estate"

class BusinessProfile(BaseModel):
    agent_name: str = Field(..., description="Persona name, e.g. 'Ate Ana'")
    business_name: str
    industry: Industry
    services: List[str] = Field(..., min_length=1)
    pricing: str = Field(..., description="Price range string, e.g. 'P500-P1500'. Never leave None.")
    phone: str

    def render_system_prompt(self, env: jinja2.Environment) -> str:
        template = env.get_template(f"{self.industry.value}.j2")
        # StrictUndefined on the env ensures missing fields raise UndefinedError here,
        # not silently render as empty string mid-conversation.
        return template.render(**self.model_dump())
```

**StageDetectionOutput** — structured output for the LLM ambiguous-transition call (D-07):

```python
class StageDetectionOutput(BaseModel):
    next_stage: Literal[
        "intro", "qualify", "pitch", "objection_handling",
        "propose_appointment", "confirm", "escalate"
    ]
    confidence: float = Field(..., ge=0.0, le=1.0)
    reasoning: str = Field(..., max_length=200)

# How to call with LiteLLM Router + instructor for structured output:
import instructor
from litellm import Router

# Patch the router client with instructor for structured extraction
# instructor wraps the acompletion call and handles JSON mode + retries
patched_router = instructor.patch(router)  # verify: instructor supports LiteLLM Router patching

async def detect_stage(messages: list, current_stage: str) -> StageDetectionOutput:
    MAX_RETRIES = 3
    for attempt in range(MAX_RETRIES):
        try:
            result = await patched_router.chat.completions.create(
                model="chat",
                messages=messages + [{
                    "role": "system",
                    "content": f"Current stage: {current_stage}. Return next_stage as JSON."
                }],
                response_model=StageDetectionOutput,
                max_tokens=100,
                temperature=0.0,   # deterministic for classification
            )
            return result
        except instructor.exceptions.InstructorRetryException as e:
            if attempt == MAX_RETRIES - 1:
                # Log and fall back to linear progression
                logger.error("Stage detection failed after 3 retries: %s", str(e))
                return StageDetectionOutput(
                    next_stage=current_stage, confidence=0.0, reasoning="fallback"
                )
```

Note: verify that `instructor.patch` supports LiteLLM `Router` instances in the installed versions. If not, call `litellm.acompletion()` directly with `response_format={"type": "json_object"}` and parse with `StageDetectionOutput.model_validate_json(response.choices[0].message.content)`, retrying on `ValidationError`.

### 4b.2 Async-First Design

LangGraph's async API (`astream`, `ainvoke`, `aget_state`) runs on asyncio. FastAPI runs on asyncio. They share the same event loop.

**The one common mistake:** calling `asyncio.run()` inside a FastAPI route or WebSocket handler. `asyncio.run()` creates a new event loop, which conflicts with the running FastAPI event loop and raises `RuntimeError: This event loop is already running`. Every LangGraph call inside FastAPI must be `await`ed directly:

```python
# WRONG — will raise RuntimeError inside FastAPI
result = asyncio.run(graph.ainvoke(...))

# CORRECT
result = await graph.ainvoke(...)
```

**Stream vs. await:**
- Use `graph.astream(..., stream_mode="messages")` for the WebSocket handler — yields token chunks as they arrive, giving the lead a real-time typing effect.
- Use `await graph.ainvoke(...)` only in non-streaming contexts (e.g., background escalation checks, test assertions). `ainvoke` waits for the full response before returning, which adds perceived latency to the demo UI.
- Do not mix: do not call `graph.astream()` and then also `await graph.aget_state()` inside the same `async for` loop — `aget_state` is safe to call after the stream completes, not during.

**AsyncPostgresSaver setup pattern with FastAPI lifespan:**
```python
from contextlib import asynccontextmanager
from fastapi import FastAPI
from langgraph.checkpoint.postgres.aio import AsyncPostgresSaver
from agent.graph import builder

compiled_graph = None

@asynccontextmanager
async def lifespan(app: FastAPI):
    global compiled_graph
    async with AsyncPostgresSaver.from_conn_string(
        os.environ["SUPABASE_DB_URI"]
    ) as checkpointer:
        await checkpointer.setup()
        compiled_graph = builder.compile(checkpointer=checkpointer)
        yield   # app runs here
    # checkpointer connection closes on exit

app = FastAPI(lifespan=lifespan)
```

### 4b.3 Prompt Engineering Discipline

**System vs. user prompt separation:**
- System prompt = rendered Jinja2 template containing BusinessProfile fields + Taglish code-switching instruction. Injected once at conversation start as `{"role": "system", "content": ...}`. Never rebuilt on every turn — the checkpointer preserves it in the messages list.
- User prompt = the lead's raw message. Never modify or annotate user messages before passing to the LLM.
- Stage instruction = appended as a separate `{"role": "system", "content": f"Current stage: {stage}. Goal: ..."}` message at the end of the messages list, before the LLM call. This keeps the stage directive current even as earlier messages scroll out of the context window.

**Few-shot:**
- Inline few-shot examples in the system prompt for the intro and objection_handling stages — these are the highest-variance stages in Tagalog sales conversation.
- Keep examples to 2 per stage (1 positive, 1 objection) to avoid bloating the system prompt. Each example adds ~100 tokens.

**Token budget:**
- Always set `max_tokens=512` explicitly. Never leave it unset in production — some LiteLLM provider backends default to unlimited, producing responses that hit context limits mid-stream without error.
- System prompt (rendered Jinja2): budget 400 tokens. If a template renders longer, truncate the `services` list.
- History: 20 messages × ~80 tokens avg = ~1,600 tokens. Total per call ≈ 2,500 tokens input + 512 output = ~3,000 tokens.

### 4b.4 Context Window Management

Llama 4 Maverick (128K) will not hit its context limit in Phase 1 demo conversations (capped at 20 turns). However, design for future phases now:

**Summarisation trigger** (implement when `len(state["messages"]) > 20`):
1. Slice messages `[1:-5]` (keep system prompt at index 0, keep last 5 turns verbatim).
2. Call `router.acompletion(model="chat", messages=slice, max_tokens=200, temperature=0.0)` with a summarisation prompt: "Summarise this sales conversation in 3 sentences, preserving: what product was discussed, objections raised, and current interest level."
3. Replace the sliced messages with a single `{"role": "assistant", "content": f"[Earlier conversation summary]: {summary}"}` message.
4. Update `state["messages"]` with the compressed list. LangGraph's `add_messages` reducer handles this correctly if you return the full new list rather than a delta.

**Do not use LangGraph's built-in `MemorySaver`** for production — it stores everything in RAM. Phase 1 uses `AsyncPostgresSaver` exclusively.

### 4b.5 Cost and Latency Budget

**Per-call cost at Groq free tier:**
- Groq/Llama 4 Maverick: free tier — $0 per call, but hard RPM/TPM limits apply
- Gemini Flash 1.5: $0.075 / 1M input tokens, $0.30 / 1M output tokens → ~$0.0002 per call at 3K tokens
- Mistral Small: ~$0.0006 per call at 3K tokens

At 50 concurrent demo sessions × 10 turns each = 500 calls/session. Free tier exhausted in < 1 minute. Budget assumption: Groq handles 80% of calls in demo (free); Gemini Flash handles overflow (~$0.10 for a full demo day of 500 spillover calls).

**Caching:**
- Enable LiteLLM in-memory cache for exact-match responses (repeated demo inputs, e.g. "Hi" or "Magkano?"): `Router(..., cache_responses=True)`. This costs nothing and removes LLM latency for common greetings.
- Do not cache with Redis in Phase 1 — adds operational complexity for a demo.

**Sub-task model routing:**
- Stage detection (D-07 ambiguous transitions): use the same `chat` model group but with `max_tokens=50`. At Groq free tier this costs 0 but uses TPM budget — route this call to Mistral Small if Groq TPM budget is near the limit.
- Conversation summarisation (context compaction): route explicitly to `mistral/mistral-small-latest` via a separate `"summariser"` model group in the Router. Prevents summarisation from consuming Groq RPM budget needed for the main conversation.

## 6. Guardrails

### Online (Real-Time)

These run on every request. Kept to the minimum necessary to avoid adding latency to the Taglish streaming response.

| Guardrail | Trigger | Intervention | Latency Budget |
|-----------|---------|--------------|---------------|
| **AI identity disclosure check** | Every intro turn (stage = "intro", turn index = 0) | Block send if the rendered intro message does not contain the required AI disclosure phrase. Log the violation to Phoenix. Render a fallback intro with hardcoded disclosure. | < 5ms (string contains check) |
| **Jinja2 BusinessProfile completeness** | Before every template render (at `agent_node` entry in intro stage) | Validate `BusinessProfile` with Pydantic before passing to Jinja2. If `ValidationError` raised: block the render, return a graceful fallback message to the lead ("Sandali lang po"), log the missing field to Phoenix, and page the operator. Do not let the WebSocket drop. | < 2ms (Pydantic validation is synchronous) |
| **Price and slot range assertion** | Any agent reply in `propose_appointment` or `confirm` stage | After the LLM reply is generated, extract any stated price (regex: `P[\d,]+`) and any stated time slot. Assert both are within BusinessProfile bounds. If out of range: suppress the reply, regenerate with an explicit constraint added to the prompt ("You MUST only propose slots from this list: {slots}"), retry once. If retry also fails: escalate to human immediately. | < 10ms (regex extraction + dict lookup) |
| **Cascading 429 circuit breaker** | LiteLLM Router raises `RateLimitError` on all 3 providers simultaneously | Halt new LLM calls for 30 seconds. Return a holding message to the lead ("Sandali lang po, may technical issue kami"). Alert the operator via WebSocket owner panel event `type: system_alert`. Resume after 30s backoff. | Handled by LiteLLM Router `retry_after` config; holding message is string, not LLM call |

### Offline (Flywheel)

These run on sampled batches after the fact and feed back into prompt improvement and escalation threshold tuning.

| Metric | Sampling Strategy | Cadence | Action on Degradation |
|--------|------------------|---------|----------------------|
| **Register matching pass rate** | 100% of conversations in the first 2 weeks of demo; drop to 20% random sample thereafter | Weekly batch run via Arize Phoenix LLM judge | If pass rate drops below 85% in a weekly batch: review failed turns with the Filipino sales manager, update the Taglish instruction in the system prompt, re-run eval dataset |
| **Escalation false positive rate** | All escalation events (100% — volume is low) | Real-time logging; weekly human review | If false positive rate exceeds 10% in any 7-day window: tighten the composite signal thresholds (raise sentiment confidence threshold or cadence window); re-run escalation test cases |

| **Persona collapse detection** | All conversations > 10 turns (stage reaches `propose_appointment` or later) | Weekly LLM judge run | If persona name drop rate exceeds 5% of long conversations: audit the stage instruction injection pattern (Section 4b.3); ensure persona name is present in the appended stage system message |
| **Appointment detail error rate** | All `propose_appointment` and `confirm` stage messages | Weekly code assertion run against BusinessProfile fixtures | Any appointment detail error triggers immediate prompt patch + re-run of the price/slot eval cases — no tolerance threshold; any non-zero rate is a P1 issue |

## 7. Production Monitoring

**Tracing Tool:** Arize Phoenix (self-hosted, open-source). No account required. Runs alongside FastAPI via the OpenTelemetry exporter configured in Section 5. Every LangGraph node span is captured automatically via `LangChainInstrumentor`. Phoenix UI at `http://localhost:6006` shows full trace trees, latency per node, and LLM token counts.

**Key Metrics to Track:**

| Metric | Source | Target |
|--------|--------|--------|
| `stage_transition_latency_p95` | Phoenix span duration for `agent_node` per stage | < 3s p95 (Groq free tier; acceptable for demo) |
| `fallback_activation_rate` | LiteLLM Router metadata on each span — count of Gemini Flash / Mistral calls vs. Groq calls | < 20% of calls on fallback (indicates Groq quota stress) |

| `websocket_drop_rate` | FastAPI WebSocket connection error count / total sessions | < 1% per demo day |
| `conversation_goal_completion_rate` | Share of threads that reach `propose_appointment` or `confirm` stage | > 60% in demo sessions (baseline; tune after first 20 demo runs) |

**Alert Thresholds:**

| Condition | Threshold | Alert Action |
|-----------|-----------|--------------|
| All 3 LiteLLM providers return 429 simultaneously | 1 occurrence | Owner panel system alert; operator Slack/email notification; 30s circuit breaker activates |
| `stage_transition_latency_p95` > 8s | Sustained > 3 minutes | Log to Phoenix; operator notification — likely Groq TPM exhaustion |
| `websocket_drop_rate` > 5% in any 15-minute window | 5% | Operator notification — likely FastAPI event loop blocking (check for sync calls in async context) |
| Appointment detail error detected by online guardrail | Any occurrence | Immediate P1 log entry in Phoenix; operator notification; suppress reply and escalate to human |
| PostgresSaver `aget_state()` returns `None` for a thread with known prior checkpoints | Any occurrence | Log as P1 (state replay failure); operator notification; restart conversation thread from stage 0 with a grace message to the lead |

**Smart Sampling Strategy:**

Conversations are reviewed by the business owner (5 randomly sampled per week) and by the eval flywheel. The signal-based filters below prioritize the highest-value interactions for human review:

1. **Escalation events (100% review)** — every conversation that reaches the `escalate` stage is reviewed by the product owner within 24 hours. Volume is low in demo; this is the highest-stakes outcome.
2. **Long conversations (> 8 turns, 100% review in first month)** — these are most likely to show persona collapse or stage-loop bugs. After the first month, drop to 50% sample.
3. **Conversations containing price mentions (20% random sample)** — spot-check appointment detail accuracy in production. The code guardrail catches hard violations; sampling catches soft ones (e.g., correct price but stated ambiguously).
4. **Conversations where the lead sent a soft-deflection phrase** — flagged automatically by a keyword filter on lead messages (`i-iisip ko`, `baka next month`, `busy muna`, `ask ko muna`) — 100% sent to LLM judge for indirect rejection classification.
5. **Conversations with WebSocket reconnects** — any thread where the WebSocket reconnected mid-conversation (detectable by a gap in turn timestamps > 60s) is reviewed for state replay correctness.

Human review is conducted in the Arize Phoenix UI using the conversation trace view. The Filipino sales manager reviews flagged conversations weekly and updates the eval dataset with any new failure patterns observed.
